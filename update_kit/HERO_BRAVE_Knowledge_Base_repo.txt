# HERO User Knowledge Base For BRAVE

**Knowledge status:** Review-ready current user guidance; publication requires process-owner approval

**Source system version:** Verified against repository `main` at `1f1e0a23` on 2026-08-27

**Audience:** HERO users, Brand Captains, KAMs, demand planners, trainers, and first-line support

## How BRAVE Must Use This Knowledge

BRAVE should:

1. Answer only from facts in this knowledge base.
2. Distinguish current behavior from planned changes.
3. Say when an operator must confirm a current run, refresh, incident, or downstream import.
4. Never claim a job completed or data is current without runtime evidence.
5. Never advise a user to edit production tables, run Databricks jobs, or directly repair Logility.
6. Ask for exact scope when troubleshooting: BU, fiscal year, forecast partner, brand, channel, SKU, workbook download time, upload time, and screenshot or annotated file.
7. Escalate suspected source-data incidents before telling users to compensate with BTA.

## 1. What HERO Is For

HERO collects business knowledge that should change the shipment forecast. It has two main workflows:

- **Enrichment:** capture an identifiable event or business reason, including dates, type, quantities or assumptions, status, and uploader.
- **Reconciliation:** enter a signed weekly Base Trend Adjustment when the remaining forecast still needs to be aligned.

Users should prefer an enrichment when there is a real business event that can be described. Reconciliation is a controlled adjustment mechanism, not the default way to rebuild an entire forecast.

HERO does not own the Logility baseline, active portfolio, fiscal calendar, final ADS3 consensus, or Resultant Forecast. HERO reads upstream data and adds HERO-authored contributions.

## 2. Choose The Right Workflow

### Use an enrichment when

- a promotion, set, sample, pre-order, TMO, phase-out, depletion, or other identifiable event changes demand
- the change has a business explanation, date range, status, and expected impact
- users need stronger traceability of who changed what and why

### Use L1 BTA when

- a forecast-partner/SKU/week needs a residual signed adjustment after known events are represented
- the adjustment belongs to one forecast partner
- the user understands the value is a delta, not a final forecast total

### Use L2.5 BTA when

- a BU-SKU/week adjustment should be authored above forecast-partner level
- the adjustment should be distributed to eligible L1 partners during post-processing
- the user understands the partner split may change with the underlying baseline proportions

Do not use BTA to hide a suspected data problem. If baseline or portfolio scope suddenly looks implausible, stop and escalate it.

## 3. Base Trend Adjustments Are Deltas

Weekly L1 and L2.5 BTA cells contain signed adjustments:

- `+500` adds 500 units.
- `-500` removes 500 units.
- blank means no newly submitted value for that cell.
- `0` is an explicit zero delta.

The BTA is not a target total. If the baseline later changes, the stored delta remains unless a user changes it. For example, a baseline of 1,000 plus a BTA of 500 produces 1,500 before other contributions. If a later source cycle changes the baseline to 1,200, the same BTA contributes 500 and the result becomes 1,700 before other contributions.

## 4. L1 And L2.5 Behavior

### L1

L1 is forecast-partner grain. The editable weekly BTA belongs to the partner shown on the row.

### L2.5

The `_ALL_FORECAST_PARTNERS_` workflow is BU-SKU grain. The user authors one weekly L2.5 delta. HERO post-processing distributes it to L1 partners using baseline proportions.

If the eligible partner slice has no baseline, HERO uses its configured fallback, currently an equal split across eligible partners. This may not preserve a separately maintained commercial allocation.

An L2.5 upload does not instantly update all L1 rows. The L2.5 event is saved first; the fan-out and L1/dashboard materialization require post-processing.

## 5. Download Fresh, Narrow Templates

A workbook is a point-in-time extract. It does not update after download.

Users should:

1. Download a fresh template immediately before working.
2. Select only the forecast partners and brands needed.
3. Avoid keeping an old workbook for days and then uploading it.
4. Coordinate when multiple people may touch the same scope.

HERO supports multiple selected forecast partners and multiple selected brands while keeping one BU and one fiscal year. Use that feature instead of an all-brand or all-partner scope when practical.

### Overlapping work and stale workbooks

If user A downloads a broad workbook, user B uploads a change in the same scope, and user A later uploads the old workbook, HERO compares user A's workbook with the latest backend state. User A's stale values can overwrite user B's work. In overlapping scope, the latest accepted upload generally wins.

Duplicate-upload protection stops the exact same workbook from being processed twice. It does not detect every stale or partially overlapping workbook.

Deleting unrelated rows before upload can reduce reconciliation overlap when the template rules allow it. Deleting an existing enrichment row is different: it does not decline or delete the stored enrichment.

## 6. Enrichment Status And Identity

To make an existing enrichment inactive, update it to the supported inactive status, normally `DECLINED`, and upload the row. Simply deleting the row from Excel does not instruct HERO to remove the event.

Do not change the SKU or forecast partner on an existing event to move it. Those fields are part of the event identity and changing them can create a new event while leaving the old event active. Decline the old event and create a new row for the new scope.

Enrichment history provides stronger user and business-context attribution than net BTA. Preserve that advantage by representing identifiable events as enrichments.

## 7. Formulas And Numeric Values

Excel formulas are supported only in weekly L1 or L2.5 BTA cells when Excel has recalculated the formula and saved a finite numeric result in the workbook.

- HERO does not calculate Excel formulas on the server.
- Open and recalculate the workbook in Excel before saving and uploading.
- A formula with no saved numeric result is rejected.
- Formulas in enrichment, identity, date, context, or read-only fields are rejected.
- Upload feedback should identify the failing sheet, row, column, and reason.

## 8. Dates, Fiscal Weeks, And Planning Cycles

An enrichment start and end date must fall within the selected template fiscal year, and the end must not be before the start. Use the workbook's date guidance and annotated upload feedback.

`Wk #` means Hasbro fiscal week for the selected fiscal year, not calendar week. Use the Calendar Reference sheet to map weeks to dates and fiscal months.

Current and previous planning cycles follow configured IBP/ADS3 cycle windows where available. A fiscal month boundary by itself does not define the planning cycle. If a cycle boundary appears wrong, escalate it with the date and workbook timestamp.

## 9. Preliminary Consensus Forecast

The template's Preliminary Consensus Forecast is a live Excel calculation that combines the visible baseline and applicable HERO contributions for that row and week. It is intended to help users see the effect of an edit before uploading.

It is not the final Logility ADS3 and is not a direct live read from Logility. L2.5-to-L1 changes still require post-processing before all partner views match.

Users should review the preliminary total, not only one adjustment column. If the preliminary total goes below zero, stop and confirm the source and business intent. HERO should preserve signed input and attribution rather than silently rewriting one user's adjustment to compensate for another.

## 10. Dashboard And Template Timing

A dashboard and template can temporarily differ because:

- they were generated at different times
- partner render refresh has not completed
- L2.5 post-processing has not completed
- Power BI has not refreshed
- filters or aggregation grain differ
- an upstream source load changed between comparisons

Before reporting a defect, align:

- BU and fiscal year
- forecast partners, brands, and channel
- SKU grain
- current versus previous cycle
- template download timestamp
- dashboard refresh timestamp

Do not ask users to correct values until the comparison uses the same scope and time.

## 11. Missing SKUs

A SKU is available only when the current demand-planning source delivered to HERO contains the exact BU, forecast partner, channel, and fiscal-year scope.

Seeing a SKU in another Logility screen or array does not guarantee it is in HERO. In particular, a field-forecast record alone may not create the demand-planning source row HERO uses for template scope.

If a SKU is missing:

1. Confirm BU, partner, channel, SKU, and fiscal year.
2. Confirm the Logility portfolio extension covers that exact scope.
3. Allow the normal Logility-to-EDW/HDC data pass.
4. Download a fresh template after the source load.
5. Escalate if the exact key remains absent.

An old workbook never gains a newly activated SKU.

## 12. What HERO Sends To Logility

Users author deltas in HERO, but the export contains complete replacement values for affected Logility array/week cells.

### Field Forecast arrays

| HERO activity | Logility array |
| --- | --- |
| Reconciliation and residual non-marketing changes | UA1, subject to its frozen window |
| Retail promotion | UA2 |
| Set | UA3 |
| Sample | UA4 |
| TMO | UA5 |
| Pre-order | UA6 |
| Marketing and demand-planning overlay | No UA array |

### Consensus inputs

- Positive eligible contributions flow to ADS2.
- Negative eligible contributions flow to Promo Lift.
- TMO is excluded from HERO's consensus export.
- HERO does not export ADS3 or Resultant Forecast.

Current configured horizons for UK and US are:

- UA1: horizon months 5-12
- UA2-UA6: horizon months 0-21
- ADS2 and Promo Lift: horizon months 0-21

HERO rounds output to whole units at partner/SKU/week grain. Small aggregate differences can result when many fractional L2.5 fan-out cells are rounded separately.

## 13. Manual And Automated Logility Integration

HERO creates governed export tables, snapshots, deltas, run metadata, and contingency files. A successful HERO export means those artifacts were produced.

It does not, by itself, prove that Logility imported them. During the pilot, generated files have also been handed off for manual Logility upload. Automated downstream pickup depends on a separate EDW/Logility integration and acknowledgement outside the HERO application.

BRAVE must not state that Logility is updated until the downstream owner confirms it.

## 14. Negative Values

HERO allows signed user adjustments and preserves them for traceability. At the export boundary, UA1-UA6 are protected from negative output. Consensus contributions are separated by sign: ADS2 carries positive values and Promo Lift intentionally carries negative values. Logility uses those inputs in its downstream consensus calculation.

HERO should not silently trim one user's L1 adjustment to preserve another user's L2.5 adjustment. That would change intent and corrupt attribution. A negative preliminary total should be reviewed and corrected through an explicit user decision.

## 15. Common Questions

### “I uploaded L2.5. Why is L1 unchanged?”

The upload saved the L2.5 event, but partner fan-out requires post-processing. Wait for the processing and dashboard refresh, then compare a fresh template at the same scope.

### “Why did my total change when baseline changed?”

BTA is a stored delta. HERO does not convert it into a fixed target total. A new baseline plus the same delta produces a new preliminary total.

### “Can I delete a row to remove an enrichment?”

No. Upload the existing event with the supported inactive status, normally `DECLINED`.

### “Can I change the partner on an enrichment row?”

Do not repurpose an existing row. Decline it and create a new event for the new partner.

### “Why can I see the SKU in Logility but not HERO?”

HERO requires the exact partner/channel/year key in its current demand-planning source. Another Logility array or screen may have the SKU without satisfying that scope.

### “Will HERO overwrite a direct Logility edit?”

Only affected cells included in a later imported HERO replacement export are overwritten. Ordinary diff logic may not resend an unchanged HERO value. An approved force republish can resend current HERO replacement values, but downstream import must still occur.

### “Does HERO export the final consensus?”

No. HERO exports UA arrays and ADS2/Promo Lift inputs. Logility calculates ADS3 and Resultant under its own process.

### “Why is a large template slow?”

Reconciliation workbooks are wide and can contain many partner/SKU rows, formulas, formatting, and validations. Use the narrowest practical partner and brand scope. Very large bulk templates take longer to render, download, open, and upload.

## 16. Escalation Checklist

Send the support team:

- environment: STG or PROD
- business unit and fiscal year
- forecast partner(s), brand(s), and channel
- planning SKU and description
- workbook filename and download time
- upload time and annotated workbook, if any
- dashboard screenshot and refresh time
- expected value and observed value
- whether the issue is baseline, enrichment, L1 BTA, L2.5 BTA, preliminary forecast, or Logility export

Do not compensate for a suspected source or display defect while it is under investigation. Preserve the workbook and examples so the team can trace the actual source.
